Each fact is tagged verified (reproduced from bytes or independent implementation), inferred (strong RE evidence, not confirmed on hardware), or unresolved (conflicting evidence).

4. The intercepted map call site
The patch replaces one instruction in the Driver Wish torque evaluation routine at 0x09B2A8:

text
0x09B2A8: addi r5, r31, 382        ; factory: 0x1D1578 + 0x17E = 0x1D16F6 (stock TL map)
         ↓ (patched to)
0x09B2A8: bl 0x1FE200              ; opcode 0x48162F59
0x09B2AC: addi r6, r1, 24          ; factory continuation, writes r6
0x09B2B0: bl 0x0F94DC              ; map lookup routine
0x09B2B4: addi r28, r3, 0
0x09B2B8: lha  r3, -27160(r13)     ; load 0x7F95D8 (X for next lookup)
0x09B2BC: lha  r4, -24400(r13)     ; load 0x7FA0A0 (Y for next lookup)
0x09B2C0: addi r5, r31, 362        ; next map
0x09B2C4: addi r6, r1, 36
0x09B2C8: bl 0x0F94DC
0x09B2CC: extsh r21, r28
0x09B2D0: neg r4, r21
0x09B2D4: bl 0x0F89B4
0x09B2D8: lha  r9, -17434(r13)     ; unconditional overwrite of r9
The enclosing function: 0x09AFDC..0x09B93C (2,404 bytes). Allocates a 152-byte stack frame (stwu r1, -152(r1)), saves its own LR at 156(r1) (= old SP + 4 in its parent's frame, not its own).

Map lookup routine 0x0F94DC semantics: r3 = X (compared against first axis, nx entries), r4 = Y (compared against second axis), r5 = map pointer. Returns interpolated value in r3.

The intercepted map's axes (stock): X = [600, 700, 890, 930] — not pedal percent. Y = rpm-like. The map is indexed by 0x7F95D8, not by the pedal gate variable 0x7F95C4. This is the fundamental mismatch flagged by the peer audit.

5. CAN 0x38A receive path (fully traced)
This is the strongest piece of RE in the project — all verified from bytes, no inference.

Frame descriptor
text
0x1C0DBC:  00 00 | 03 8A | 01 00 | 03 00 | 04 00 | 00 00
           Pad     CAN ID  Flags   Group=0   DLC=4  Pad
0x1C0DC8:  10 01 00 02       ; 20 ms repetition, max 2 timeouts
Group 0, block 3 → hardware acceptance filter bank at 0x707130.

Active CAN Message Table entry 21
Table base 0x0413F8, 43 records × 20 bytes. Entry 21 at 0x04159C:

text
0x04159C: 15 00 00 00    ; tag = 21 / handle 0x15
0x0415A0: 00 00 00 00    ; callback = none
0x0415A4: 01 1C 0D C8    ; trailer pointer
0x0415A8: 01 1C 0D BC    ; config pointer → ID 0x38A
0x0415AC: 00 7F F1 20    ; buffer pointer → 0x007FF120
0x007FF120 appears exactly once in the entire 2 MB image — at 0x0415AC. This is the single cross-reference that proves the buffer is dedicated to this frame.

Delivery routine 0xFB6F4
text
0xFB704: lwz  r11, 0x86(r12)     ; load CAN payload bytes 0-3
0xFB708: lwz  r10, 0x8A(r12)     ; load payload bytes 4-7
0xFB70C: stw  r11, 0x00(r4)      ; store bytes 0-3  → 0x7FF120
0xFB710: stw  r10, 0x04(r4)      ; store bytes 4-7  → 0x7FF124
Bytes are copied verbatim in order. Therefore 0x007FF122 = CAN payload byte 2 — confirmed, not inferred.

GRA_Neu byte layout
Byte	Address	Meaning
0	0x7FF120	checksum / CRC
1	0x7FF121	main cruise switch (Bit 0) + status bits
2	0x7FF122	Bit 0 = SET, Bit 1 = RESUME, Bit 2 = CANCEL, Bits 4-7 = rolling counter
3	0x7FF123	tip down/up + status (not "unused")
Bit assignments within byte 2 are inferred from community opendbc GRA_Neu_Setzen / GRA_Recall naming, not confirmed from this ECU. No OS code reads 0x7FF120..0x7FF127 anywhere in the image — there is no in-binary cross-check. Only a bench CAN capture with a real stalk press can confirm which bit the J527 actually sets.

DFES trap — do not confuse with the button
Flag 0x1B3 at 0x6F82A3/0x7FF18D in the 456-flag DFES matrix is a fault qualification byte (CAN 0x38A communication timeout DTC status), not the button. Disassembly at 0x858CC and 0x85960 confirms: it reads fault notification entries, tests bit masks, and sets ISO 14229 status byte 0x11 (TestFailed). It will never toggle on a human press.

9. Checksums
Bosch EDC16 convention: each region's 32-bit big-endian word sum is balanced to 0xD01FE500 by a 4-byte complement stored at the end of the region. This is an additive sum, not a CRC.

Region	Span	Expected total
OS	0x040000..0x17FFFF	0xD01FE500
Cal1	0x180000..0x1BFFFF	0xD01FE500
Cal2	0x1C0000..0x1FDFFF (end unresolved, see below)	0xD01FE500
Reported raw sums have changed between document revisions for the same binary. Two sets exist:

Region	Set A (Round 2)	Set B (later report)
OS raw	0x4A23523C	0x93308967
Cal1 raw	0xF940B5DC	0xE63943CA
Cal2 raw	0xC9E01A9E	0x9D58E2F2
Both sets balance to 0xD01FE500 with their respective complement words, but they cannot both be correct for the same binary with the same algorithm over the same regions. Re-run verify_checksums.py fresh and commit the raw stdout before relying on either set.

Cal2 span end — unresolved. Balance word is reported as both 0x1FDFFC (implying span end 0x1FDFFF) and 0x1FFEF8 (implying span extends into 0x1FE000..0x1FFFFF, i.e., covers the patch code). If the second is true, the patch code is factory-protected and the "accept-and-document" residual-risk decision is moot. Resolve from boot block (internal flash) once BDM read is available.

11. Open questions (ranked by impact on further RE)
Cal2 span end — 0x1FDFFF or further? Determines whether the patch code is checksum-protected. Resolve from boot block or by finding the checksum routine's span constants in OS disassembly.

Checksum raw sums — which set is correct? Re-run verify_checksums.py, save raw stdout.

Pedal gate variable identity — 0x7F95C4 vs 0x7F95D8. Higher-confidence RE would need: disassemble 0x636F0 (what kind of processing does 0x7F95C4 undergo?), identify map at 0x595C4 (what is 0x7F95C4 controlling?), check neighbors 0x7F95C2/0x7F95C6, or cross-reference to community damos/A2L files for EDC16U34.

SET bit within 0x7FF122 — bench CAN capture required. Bit 0 = SET is from community DBC.

Warm-reset RAM behavior — internal flash read or bench dump.

Boot block contents — nothing in this project has seen the real boot block. First BDM read reveals it.

12. Caveats for future disassembly
File offsets = CPU code addresses for the external flash region. No translation needed.

stock_382083.ori is not a full image. Any analysis assuming the boot region is "supposed to be 0xFF" is wrong. The real ECU has code there.

Static-only. Nothing in this document was observed on a running ECU. Every RAM address, every register fact, every call-site trace comes from static disassembly of stock_382083.ori or from emulator behavior.

The emulator implements only the ISA subset the patch uses. It cannot run OS boot code, the CAN driver, the diagnostic task, or anything else outside the three patched regions. Claims about OS behavior derived from the emulator are claims about the model, not the machine.

The DFES flag 0x1B3 is a trap. It appears in 456-flag tables and looks like a live signal. It is not — it is a fault qualification byte. Disassembly at 0x858CC proves this.

The bit meaning of 0x7FF122 Bit 0 vs Bit 1 is not encoded anywhere in the binary. It comes from a community DBC. If a future disassembly of the J527 module's firmware is ever possible, that's the authoritative source.

Z3 proofs are against a semantic model of the opcodes, not the silicon. The proof holds if and only if the AST faithfully represents PowerPC semantics for those 26 instructions. The test_symbolic_thunk.py script verifies the byte identity of the opcodes against the candidate and models their semantics — so the fidelity chain is: candidate bytes → disassembly → AST. A transcription error in the AST would invalidate the proof without failing the byte assertion.

That's the complete reference. The strongest verified material is §5 (CAN receive path) and §6 (patch disassembly) — both proven from bytes with zero inference. The weakest is §3 (RAM zeroing) and §11 (open questions) — those are the things bench work exists to settle.
